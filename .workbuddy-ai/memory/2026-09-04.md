## Arabic (ar) localization sweep across 10 pages + 2 dead buttons

### Root cause of "English shows while lang = ar"
`TranslationService.get()` (angular/src/app/core/services/translation.service.ts) returns **the key
itself** when it has no entry in `assets/i18n/ar.json`. It backs onto two mechanisms:
1. `TranslatePipe` → `get(key)` for `{{ 'Key' | translate }}` bindings.
2. A `MutationObserver` DOM walker (`translateElement`) that translates **raw text nodes** and
   `input[placeholder]` after every mutation — so plain English in a template (no pipe) also gets
   translated, as long as the key exists in ar.json.

So the fix for "X renders in English" is almost always **add the key to ar.json**, not edit the
template. Verified: toasts (toast-container) and confirm dialogs (confirm-dialog) render as plain
text nodes, so they are covered by mechanism 2 as well.

### Two bugs that a dictionary entry can NOT fix
- **Mixed Arabic/English in one text node.** `processTextNode` bails out early if the node contains
  any Arabic char (`if (/[\u0600-\u06FF]/) return;` in ar mode). So `{{ 'HR:AnnualLeave' | translate }}
  Balance` renders "إجازة سنوية Balance" forever. Fix: split into two interpolations.
- **Template-literal messages** (e.g. `Are you sure you want to delete ${name}? This action cannot be
  undone.`) never match a static key. Fix: add a regex to `matchDynamicToast()` in
  translation.service.ts (both the to-Arabic and the reverse Arabic->English branch).
