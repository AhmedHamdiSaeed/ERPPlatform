## Session Lifetimes: 3h Desktop / 6 Months Mobile (+ silent token refresh)

Mobile requirement: session = 6 months (180 days), desktop stays 3 hours.

- `core/utils/device.util.ts` (new) — `isMobileDevice()`: UA keywords OR (touch + coarse pointer +
  width < 1024) so iPadOS 13+ (which reports as Macintosh) is detected
- `session.constants.ts` — added `MOBILE_SESSION_DURATION_MS` (180d), `MAX_TIMEOUT_MS`,
  `REFRESH_TOKEN_KEY`
- `session-timeout.service.ts` — `start()` now picks the duration via `resolveDuration()`
  (dev override > mobile 6mo > desktop 3h). Removed the separate warn `setTimeout`; the 30s tick
  now emits the 5-minute warning.
- **Critical fix:** `setTimeout` overflows past 2^31-1 ms (~24.8 days) and fires immediately, which
  would have logged mobile users out instantly. The expiry wait is now capped at `MAX_TIMEOUT_MS`
  and re-armed until the real expiry.

### Making the 6 months real (server tokens)
The client session alone is cosmetic: ABP/OpenIddict access tokens die after ~30 min → 401 → logout.
- `auth.service.ts` — stores `refresh_token`, `refreshSession()` (single in-flight refresh shared by
  concurrent 401s, `grant_type=refresh_token`), revoke on logout via `/connect/revocation`
- `auth.interceptor.ts` — on 401: refresh then replay the request once (guarded by an
  `X-Auth-Retry` header so it can never loop); no refresh token or failed refresh →
  `session.expire('unauthorized')`. AuthService is pulled from `Injector` lazily to avoid the
  HttpClient ⇄ interceptor DI cycle.
- `Host/ERPPlatform.HttpApi.Host/ERPPlatformHttpApiHostModule.cs` — new `ConfigureTokenLifetimes()`:
  `Configure<OpenIddictServerOptions>` sets AccessTokenLifetime (30 min) and RefreshTokenLifetime
  (180 days), both overridable via `Auth:AccessTokenLifetimeMinutes` / `Auth:RefreshTokenLifetimeDays`
  in appsettings.json (values added there).

## Global Resumable File Import Feature (chunked upload + background job + real-time done notification)

Requirement: a global "Import" available on every page; the file is sent in chunks; if a request
fails mid-upload, re-uploading resumes from the last received chunk (e.g. 30%, not 0%); when the
server finishes processing it pushes a real-time notification "upload finished successfully".

### Backend (DONE, built 0 errors to temp output)

  `start` (creates ImportSession blob in container `file-imports`, returns uploadId),
  `chunk` (multipart, `MaxChunkBytes=20MB`, saves chunk + records ReceivedIndices),
  `status` (returns receivedIndices/totalChunks/percent/status — this is what drives resume),
  `complete` (concatenates chunks into `final/{fileName}`, sets status=Processing, enqueues job).

  `AsyncBackgroundJob<FileImportJobArgs>`; injects `IHubContext<NotificationHub>` and on finish

### Added Excel/CSV file-type validation (both ends)
User asked to validate the imported file type on frontend AND backend (defense in depth).
- Frontend: `FileImportService.ALLOWED_EXTENSIONS = ['.xlsx','.xls','.csv']` + `isFileTypeAllowed(file)`;
  dialog rejects non-matching files immediately (new `state='invalid'` with a clear error + "Choose a
  different file" button) and the `<input accept=".xlsx,.xls,.csv">` filters the picker.
- Backend: `FileImportController` — `Start` rejects extensions not in `AllowedExtensions`
  (.xlsx/.xls/.csv, case-insensitive); `Complete` reassembles the final blob then calls
  `IsValidExcelOrCsv(byte[], fileName)` which checks magic bytes: .xlsx/.xlsm → ZIP `PK\x03\x04`,
  .xls → OLE2 `D0 CF 11 E0 A1 B1 1A E1`, .csv → reject `MZ` executables. So a renamed binary
  named .xlsx is still rejected. Both builds verified 0 errors.
