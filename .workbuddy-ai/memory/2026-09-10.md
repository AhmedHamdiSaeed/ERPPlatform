## Fixed: Angular `/api/abp/application-configuration` → "0 Unknown Error"

Three separate faults stacked up. All diagnosed and (except the last) fixed.

### 1. Backend was not listening on 44327
- `netstat` showed nothing on 44327; no `iisexpress.exe` either — backend simply wasn't started.
- I had previously launched it with `dotnet run --no-launch-profile`, which **ignores
  `launchSettings.json`** → Kestrel bound `http://localhost:5000` (and `Hosting environment: Production`).
- Correct command: `cd Host/ERPPlatform.HttpApi.Host && dotnet run --launch-profile "ERPPlatform.HttpApi.Host"`
  → binds `https://localhost:44327`, `Hosting environment: Development`.
- **Never use `--no-launch-profile` for this solution** — the profile is the only thing supplying
  `applicationUrl` and `ASPNETCORE_ENVIRONMENT=Development`.

### 2. Missing DB tables (`Invalid object name 'AppEmployeeImportJobs'`)
- `EmployeeImportMaintenanceHostedService` threw SqlException 208 every 30s:
  "Employee import maintenance sweep failed; retrying next interval."
- Fix: `cd Shared/ERPPlatform.DbMigrator && dotnet run` → succeeded (host + Acme/AlAmal/TechFlow tenants).
- Verified via sqlcmd against `(LocalDb)\MSSQLLocalDB`, database `ERPPlatform`:
  `AppEmployeeImportJobs`, `AppEmployeeImportChunks`, `AppEmployeeImportErrors` now exist.
- Note: `Shared/ERPPlatform.DbMigrator/appsettings.secrets.json` now points at **LocalDB**
  (`Server=(LocalDb)\MSSQLLocalDB;Database=ERPPlatform;...`), NOT the unreachable
  `db66804.databaseasp.net` (→ `10.0.0.31:1433`). The non-secret `appsettings.json` still has the
  remote host but the secrets file wins.
- `sqlcmd` IS available on this machine — handy for quick table checks.

### 3. Untrusted ASP.NET Core dev certificate (STILL OPEN — needs a human click)
- This is the actual cause of the literal "**0** Unknown Error": the browser kills the
  cross-origin fetch at TLS handshake, so there is no HTTP status to report.
- `curl --noproxy '*' https://localhost:44327/...` → exit 60, `schannel: SEC_E_UNTRUSTED_ROOT`.
  With `-k` it returns 200. Confirms cert, not routing.
- The Angular dev server does **not** use a proxy (no `proxy.conf.js`), so the browser talks to
  `https://localhost:44327` directly → cert must be trusted. OpenID discovery
  (`/.well-known/openid-configuration`) is fetched the same way, so a proxy workaround would also
  need the issuer to match — not worth it.

**Remedy the user must run themselves (one command, click "Yes" on the Windows dialog):**
```
dotnet dev-certs https --trust
```
Then fully restart the browser.

#### Why I could not do it for them (all tried, all failed)
| Attempt | Result |
|---|---|
| `dotnet dev-certs https` — status | 1 cert, `CN=localhost`, **not trusted** (valid to 2027-05-28) |
| PowerShell `X509Store('Root','CurrentUser').Add()` | "The operation was canceled by the user" — Windows raises a CryptUI dialog |
| `certutil -user -addstore Root` | `0x800704c7 ERROR_CANCELLED` — same dialog |
| `New-ItemProperty` on `HKCU:\...\SystemCertificates\Root\Certificates\<thumb>` | reports OK, key never appears (sandbox + Windows Protected Roots) |
| same, with `dangerouslyDisableSandbox: true` | same — key still absent in a fresh session |
| `reg import` | `reg.exe` is on the sandbox Program Blacklist (cannot be bypassed) |

**Lesson: Windows "Protected Roots" blocks all non-interactive writes to the Root store.
Do not burn time on this again — hand the user `dotnet dev-certs https --trust`.**

Also found: a **second, expired** `CN=localhost` dev cert (`6E3387BF…`, expired 2026-06-20) still
sits in `Cert:\CurrentUser\My`. Harmless, but `dotnet dev-certs https --clean` would tidy it.

## Swagger in production ("show all APIs after deploy")

**Finding: Swagger was already enabled in Production and already listed every API — nothing was
gated behind `IsDevelopment()`.** Verified empirically by running the built DLL with
`ASPNETCORE_ENVIRONMENT=Production`, which is a faithful test of the production code path
(`Program.cs` only has `#if DEBUG` around the Serilog minimum level):
```
cd Host/ERPPlatform.HttpApi.Host/bin/Debug/net9.0
ASPNETCORE_ENVIRONMENT=Production ASPNETCORE_URLS=http://localhost:5055 dotnet ERPPlatform.HttpApi.Host.dll
```
- `/swagger/index.html` → 200; `/swagger/v1/swagger.json` → **339 paths**, byte-identical to dev.
- `ConfigureSwaggerServices` + `app.UseSwagger()`/`UseAbpSwaggerUI` are called unconditionally in
  `ERPPlatformHttpApiHostModule` — no env guard anywhere.
- Rate limiter is 200 req/min per user/IP, so Swagger page loads are unaffected.

### What was actually broken (and fixed)
`AddAbpSwaggerGenWithOAuth(configuration["AuthServer:Authority"], ...)` baked
`https://localhost:44327/connect/authorize|token` into the document. On a deployed box the
"Authorize" button would send the browser back to the developer's machine.

Two edits in `Host/ERPPlatform.HttpApi.Host/ERPPlatformHttpApiHostModule.cs` (`OnApplicationInitialization`):
1. `app.UseSwagger(options => options.PreSerializeFilters.Add(...))` — rewrites every OAuth2
   scheme's `authorizationUrl`/`tokenUrl` to `{scheme}://{Host}{PathBase}/connect/...` per request.
   Valid because this host **is** the OpenIddict server, so the same-origin derivation is always
   right. `PreSerializeFilters` run after all document/operation filters, so it wins over ABP.
   Iterates all schemes with `Type == OAuth2` rather than hardcoding ABP's "oauth2" key.
2. `c.SwaggerEndpoint("v1/swagger.json", ...)` — made relative. The absolute `"/swagger/..."`
   404s under an IIS application alias or reverse-proxy sub-path.

Verified: from `Host: api.example.com` the doc now yields `http://api.example.com/connect/authorize`;
on localhost it still yields `https://localhost:44327/...`. Path count unchanged at 339.

### Still config, not code — needed for a real deploy
- `Shared/ERPPlatform.DbMigrator/appsettings.json` → `OpenIddict:Applications:ERPPlatform_Swagger:RootUrl`
  is `https://localhost:44327`. `OpenIddictDataSeedContributor` (line ~124) builds the redirect URI
  as `{RootUrl}/swagger/oauth2-redirect.html`. **Must be changed to the deployed URL and
  `dotnet run` the DbMigrator again**, or OpenIddict rejects the Swagger OAuth redirect.
- `Host/.../appsettings.json` `AuthServer:Authority` / `App:SelfUrl` are also localhost; overridable
  with no code change via env vars `AuthServer__Authority`, `App__SelfUrl`, `App__CorsOrigins`,
  `ConnectionStrings__Default`.
- Docker prod (`Dockerfile.backend` + `docker-compose.prod.yml`) runs `ASPNETCORE_URLS=http://+:8080`,
  `ASPNETCORE_ENVIRONMENT=Production` → Swagger will be at `http://<host>:8080/swagger`.

## Deployed site 500 on EVERY url (incl. /swagger/index.html)

Reported as "after deploy, adding /swagger/index.html shows nothing". **Not a Swagger issue at all.**

### Deployment facts
- Target is **IIS WebDeploy**, not Docker: `Host/ERPPlatform.HttpApi.Host/Properties/PublishProfiles/
  site89599-WebDeploy.pubxml` → `MSDeployServiceURL=site89599.siteasp.net`,
  `DeployIisAppPath=site89599`, site URL **`http://erpplatform.runasp.net/`** (deployed at ROOT, no
  application alias). Two identical profiles (`…-WebDeploy.pubxml`, `…-WebDeploy1.pubxml`).
- Production DB: **`db66804.public.databaseasp.net`** → `5.9.179.197`, **port 1433 OPEN**, db `db66804`,
  user `db66804`. Credentials already sit in `Shared/ERPPlatform.DbMigrator/appsettings.json`
  (plaintext, committed). Note the `.public.` variant is the reachable one; the bare
  `db66804.databaseasp.net` resolves to private `10.0.0.31` and is NOT reachable.
- Live probe: `/`, `/swagger/index.html`, `/swagger/v1/swagger.json`,
  `/api/abp/application-configuration` all → **HTTP 500**.
- `web.config` has `stdoutLogEnabled="false"`; the app's own Serilog sink writes `Logs/logs.txt`,
  so fetch that from the server (FTP) to see the real exception.

### Root cause
The deployed app was connecting to **LocalDB**, which does not exist on shared hosting.
**Reproduced exactly**: running the app with an unreachable DB makes even `/swagger/index.html`
return 500 (ABP's localization/multi-tenancy middleware touches the DB before Swagger's
static UI is served). So "Swagger is blank" is really "the app has no database".

### CRITICAL: appsettings.secrets.json wins over EVERYTHING
Verified empirically (three probe runs), not assumed:
| Source set to a bogus server | Result | Conclusion |
|---|---|---|
| `appsettings.Production.json` | app **started fine** on LocalDB | secrets overrides it |
| `ConnectionStrings__Default` env var | app **started fine** on LocalDB | secrets overrides **env vars** |
| both, after deleting `ConnectionStrings` from secrets | app **failed** with `server 'bogus-probe.invalid'` | `appsettings.Production.json` finally took effect |

ABP's `builder.Host.AddAppSettingsSecretsJson()` (called in `Program.cs`) appends
`appsettings.secrets.json` as the **last** configuration source — after `appsettings.{Env}.json`,
after environment variables, and after command-line args. Since the file is also **published to the
server**, it pinned every environment to LocalDB.

**Fix applied:** removed the `ConnectionStrings` block from
`Host/ERPPlatform.HttpApi.Host/appsettings.secrets.json` (kept `StringEncryption` + `Auth`).
Dev then falls back to `appsettings.json` LocalDB; Production picks up `appsettings.Production.json`.
- New file `Host/ERPPlatform.HttpApi.Host/appsettings.Production.json` (ConnectionStrings + SelfUrl +
  ClientUrl + CorsOrigins + RedirectAllowedUrls + AuthServer:Authority, all `http://erpplatform.runasp.net`).
- Added `**/appsettings.Production.json` to `.gitignore` (line 260) — it holds a password.
- Verified afterwards: dev backend still 200 on `/swagger/index.html` and
  `/api/abp/application-configuration`; Swagger still serves 339 paths.
